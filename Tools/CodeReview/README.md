# 코드 리뷰 도구

코드를 리뷰해 지적을 정해진 JSON으로 남기는 워크플로 스크립트 둘이다. 리뷰부터 이슈 등록까지의 전체 흐름은 스킬 `/review-to-issues`(`.claude/skills/review-to-issues/SKILL.md`)가 이 스크립트를 불러 진행한다.

처음에 기본 `/code-review`를 써 본 뒤, 그 구조(영역을 나눠 에이전트가 읽고, 지적마다 실패 상황을 적는다)를 바탕으로 만들었다. 결과를 기록으로 남기고, 지적을 테스트로 판정하는 흐름은 여기에 더한 것이다.

## 필요한 것

- Claude Code의 Workflow 도구: 리뷰 스크립트를 돌린다
- Python 3: 이슈 도구 `Tools/ReviewIssues/review_issue.py`가 쓴다. 표준 라이브러리만 쓴다
- GitHub CLI(`gh`): 이슈를 등록하고, 판정 커밋이 푸시됐는지와 같은 지적의 이슈가 있는지 확인한다. 저장소에 로그인해 있어야 한다
- Git
- 판정 단계의 테스트 실행에 필요한 것은 `Tools/Testing/README.md`에 있다

## 전체 흐름

```
리뷰 (이 폴더)
→ 판정: 지적마다 실패하는 테스트를 쓰고 돌린다 (Tools/Testing/)
→ 판정 커밋: 리뷰 원본과 테스트를 올린다
→ 이슈 등록: 모든 지적을 판정과 함께 (Tools/ReviewIssues/, .github/ISSUE_TEMPLATE/review-finding.yml)
→ 수정: Fixes #번호
```

- 이유: 리뷰의 지적은 추측이다. 지적 하나의 결말(재현됨, 아니었음, 의도, 넘김, 고침)이 그 지적의 이슈 하나에 출처, 증거와 함께 남는다. 재현하지 못한 지적도 무엇을 확인했는지 기록이 남아, 리뷰 도구가 얼마나 맞았는지 셀 수 있다. 열린 이슈는 `reproduced`뿐이라 추측이 할 일로 섞이지 않는다.

## 두 스크립트

| 스크립트 | 범위 | 쓰는 때 |
|---|---|---|
| `diff-review.workflow.js` (diff 리뷰) | 두 커밋(`base`..`commit`) 사이에 바뀐 코드 | 기능(feat)을 마친 뒤. 기본 |
| `review.workflow.js` (전체 리뷰) | 맡은 폴더의 파일 전부 | 출시 뒤 쌓인 버그를 한 번에 찾거나, 리뷰 도구를 측정할 때처럼 폴더 전체가 대상일 때만 |

- **diff 리뷰**: 에이전트는 바뀐 파일을 끝까지 읽고, 바뀐 것을 쓰는 곳을 따라 System과 World의 호출 순서까지 읽는다. 지적은 바뀐 줄과, 바뀐 줄 때문에 잘못 동작하게 된 곳에만 단다. 영역은 바뀐 파일을 개념 폴더로 묶어 만들고, 바뀐 줄이 1,000줄 안팎이 될 때마다 하나씩 나눈다.
- **전체 리뷰**: diff와 상관없이 지적한다.
- 이유: 전체 리뷰는 feat가 여러 폴더를 건드리면 결국 프로젝트 전체를 읽는다. 2026-11-15 측정에서 한 번에 에이전트 토큰이 100만 가까이 들었고, diff 리뷰는 2026-11-16 측정에서 약 8만이었다(아래 측정).
- 2026-11-14의 전체 리뷰는 1.0.0 출시 뒤 쌓인 버그를 한 번에 찾은 예외다.

## 실행 값(`args`)

스크립트는 바뀌지 않는 부분(결과 형식인 JSON 스키마, 공통 지침)만 가진다. 리뷰마다 바뀌는 값은 실행할 때 `args`로 넘기고, 넘기기 전에 사용자에게 보여 준다.

| 값 | 뜻 |
|---|---|
| `date` | 리뷰한 날짜 |
| `commit` | 리뷰한 커밋. 지적의 위치 링크가 이 커밋의 줄을 가리킨다 |
| `base` | diff 리뷰의 시작 커밋 |
| `context` | 이번 리뷰의 상황 설명 |
| `areas` | 영역 목록. diff 리뷰는 `files`, 전체 리뷰는 `scope`를 준다 |

- 이유: 범위와 상황이 스크립트에 박혀 있으면 리뷰마다 스크립트를 고치거나 복사해야 하고, 무엇이 바뀌었는지 흐려진다.

## 리뷰 원본

- `Docs/Reviews/`에 리뷰마다 `날짜-주제.json` 하나로 둔다. 리뷰 도구가 낸 원본이고, 고치지 않는다.
- 원본에는 실행할 때 넘긴 `args`(날짜, 커밋, `base`, 상황 설명, 영역 목록)와 지적이 함께 들어 있다.
  - 이유: 원본만 보고 무엇을 어떤 범위로 리뷰했는지와 지적의 출처를 알 수 있다.
- 예외: 범용 도구를 만들기 전의 리뷰(`2026-11-14-game-code-review`)는 원본에 커밋이 없어, 이슈 도구에 `--commit 45ba8812`를 준다.

## 결과 형식을 바꿀 때

지적의 JSON 스키마를 바꾸면 넷을 함께 바꾼다. 넷이 같은 필드 목록을 쓴다.

- `diff-review.workflow.js`
- `review.workflow.js`
- 이슈 폼 `.github/ISSUE_TEMPLATE/review-finding.yml`
- 이슈 도구 `Tools/ReviewIssues/review_issue.py`

워크플로 스크립트는 다른 파일을 불러올 수 없어 스키마를 두 스크립트에 따로 둔다.
