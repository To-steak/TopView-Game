# 2026-11-15 심은 버그 측정

## Abstract
코드 리뷰 도구(`Tools/CodeReview/review.workflow.js`)가 버그를 얼마나 찾는지 재려고, 게임 코드에 난이도가 다른 버그 10개를 일부러 심고 같은 조건으로 리뷰를 세 번 돌렸다. 리뷰는 10개 중 9, 8, 9개를 찾았다(평균 재현율 86.7%). 쉬운 버그는 모두 찾았지만, 한 틱 차이로 생기는 버그는 세 번 모두 놓쳤다. 찾은 지적은 모두 원인과 실패 상황까지 맞게 짚었다. 같은 버그라도 실행에 따라 놓치는 경우가 있었다.

## Method

### 대상
- 기준 커밋은 [a16a4b78](https://github.com/To-steak/TopView-Game/commit/a16a4b78)(main)이다.
- 버그는 커밋하지 않은 작업 트리에 심고, 측정이 끝난 뒤 되돌렸다. 심은 코드는 남기지 않았다. 버그마다의 위치, 바꾼 내용, 결과는 `answer-key.json`에 있다.

### 심은 버그
- 기능(feat) 작업이 게임 코드 전체에 흩어지는 것처럼 버그도 흩어 심었다. Systems 5개, Utilities 2개, UserInterface 2개, Presentation 1개 파일이다.
- 난이도는 쉬움 3, 중간 4, 어려움 3이다.
  - 쉬움: 한 줄 안에서 보이는 것
  - 중간: 다른 파일 하나를 따라가야 결과가 보이는 것
  - 어려움: 한 틱 차이, 칸 재사용(generation), 두 경로의 불일치
- 버그와 같은 파일에서 바로 모순되는 주석은 함께 고쳐, 주석만 보고 찾을 수 없게 했다(6번, 8번). 다른 파일의 주석(예: `World.cs`의 순서 주석)은 그대로 두었다.
- 기존 테스트(EditMode 30개, PlayMode 17개)는 버그를 심은 뒤에도 모두 통과했다. 그래서 이 측정은 테스트가 아니라 리뷰어를 잰다.

### 리뷰 실행
- 세 번 모두 같은 값(`review-args.json`)으로 동시에 돌렸다. 영역은 다섯 개다.
  - A1: Core
  - A2: 엔티티와 데이터
  - B1: 시스템(행동·공격·이동)
  - B2: 시스템(판·전리품·생성·강화·체력)과 Utilities
  - C1: Presentation과 UserInterface
- 영역 설명은 정답을 가리키지 않도록 일반적인 문장으로 썼다.
- 오염을 막기 위해 두 가지를 했다.
  - 정답지는 리뷰가 끝날 때까지 저장소 밖에 두었다.
  - 상황 설명에서 git 명령을 쓰지 말라고 했다.
  
  리뷰가 끝난 뒤 에이전트 기록을 확인했고, git 사용과 정답지 접근은 없었다.
- run1의 A1·A2와 run3의 A2는 사용량 한도로 실패해 같은 runId로 이어서 다시 돌렸다. 이 영역들에는 심은 버그가 없어 재현율에는 영향이 없다.
- 원본(`run1~3.json`)은 리뷰 도구가 낸 그대로다. 줄 번호는 버그를 심은 작업 트리 기준이다.

### 채점
- **찾음**: 심은 파일 ±5줄, 또는 그 버그의 결과가 드러나는 호출처에 단 지적이, 심은 것과 같은 원인을 짚었다.
- **부분**: 위치는 맞는데 원인이 다르다.
- 버그마다 맞은 지적 번호는 `score.json`에 있다. 지적 번호는 원본의 `result.areas[].findings[]`를 순서대로 이어 센 번호다.

## Discussion

### 한 틱 차이는 리뷰로 찾지 못했다
8번은 세 번 모두 놓쳤다. 지운 조건(`elapsedTicks == 0`)은 코드에 흔적이 남지 않는다. 찾으려면 `World.cs` 96줄의 순서 주석과, `EnemyStateChangeSystem`이 같은 틱에 상태를 바꾼다는 사실을 함께 맞춰 봐야 한다. 리뷰어는 있는 코드의 오류는 잘 찾지만, 빠진 조건이 만드는 시점 차이는 찾지 못했다. CLAUDE.md의 "한 틱 차이 버그는 확인 방법이 테스트뿐"이라는 판단과 맞는다.

### 한 번의 리뷰는 놓칠 수 있다
6번(마나 회복 지연)은 실행마다 결과가 갈렸다. run1에서는 B1이 호출처(`PlayerMoveInputSystem`)에서 찾았고, run3에서는 B2가 `PlayerManaUtility`에서 찾았으며, run2에서는 아무도 찾지 못했다. 쉬운 버그는 매번 찾았지만, 파일을 하나 건너야 보이는 버그는 실행에 따라 놓칠 수 있다.

### 같은 버그를 여러 영역이 함께 찾는다
3번(재장전)은 세 번 모두 B1(`PlayerStateSystem`)과 B2(`PlayerWeaponUtility`)가 따로 적었다. run3에서는 7번을 A2도 `EnemyDefinition` 쪽에 적었다. 호출처를 따라가 읽으라는 지침 때문이다. 이슈로 옮길 때 같은 뿌리로 묶어야 한다.

### 심지 않은 곳의 지적
세 번 모두 나온 지적은 따로 확인할 만하다. 다만 이번 측정에서는 확인하지 않았으므로, 진짜 버그인지는 모른다.
- 남은 시간을 내림해 마지막 1초 동안 `00 : 00`이 보인다 (`RemainingTimePresenter.cs:31`)
- 처치 점수만 짝수 쪽 반올림(`Mathf.RoundToInt`)을 쓴다 (`DamageSystem.cs:116`, `EnemyDefinition.cs:17`)
- `PlayerUnstuckSystem`이 사망 상태의 플레이어도 옮긴다

사망 연출 중에도 강화 화면이 열린다는 지적은 run2와 run3에서 나왔다. 기존 결정은 "HUD만 사망한 플레이어도 찾고, 강화는 거른다"이다. 이 결정에 비추어 버그인지 의도인지 확인이 필요하다.

### 한계
- 버그를 심은 쪽(Claude)이 리뷰 도구와 같은 모델이라, 고른 버그가 이 모델이 찾기 쉬운 쪽으로 기울었을 수 있다.
- 버그 하나가 한 파일의 한두 줄 변경이다. 실제 기능 작업의 버그는 여러 파일에 걸치고 diff가 더 크다.
- 심지 않은 곳의 지적을 확인하지 않아 정밀도(맞는 지적의 비율)는 재지 않았다.
- 비용이 크다. 리뷰 범위가 바뀐 줄(diff)이 아니라 폴더라서, 에이전트가 맡은 폴더의 파일을 모두 끝까지 읽는다. 호출처를 따라가며 다른 영역의 파일도 겹쳐 읽는다. feat 작업은 여러 폴더를 건드리므로 리뷰 범위가 결국 프로젝트 전체(약 1만 3천 줄)가 된다. 리뷰 한 번에 에이전트 토큰이 100만 가까이 들었고, 세 번을 동시에 돌리다 사용량 한도에 걸려 일부 영역이 실패했다.

  | 실행 | 첫 실행 | 실패 영역 재실행 | 합계 |
  |---|---|---|---|
  | run1 | 약 97만 | 약 40만 (A1·A2) | 약 137만 |
  | run2 | 약 96만 | 없음 | 약 96만 |
  | run3 | 약 94만 | 약 22만 (A2) | 약 116만 |
  | 합계 | | | 약 350만 |

  넓게 읽어서 찾은 버그도 있다. 6번은 다른 파일을 따라가야 보이는 버그였다. 따라서 범위를 줄이면 비용은 줄지만 재현율이 함께 떨어질 수 있다.
