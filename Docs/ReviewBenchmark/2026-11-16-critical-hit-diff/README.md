# 2026-11-16 가짜 feat로 diff 리뷰 측정

## Abstract
diff 리뷰 도구(`Tools/CodeReview/diff-review.workflow.js`)가 버그를 찾는지, 참조를 따라가며 비용을 얼마나 쓰는지, diff 밖의 코드를 지적하지 않는지 재려고 가짜 feat(치명타)를 만들었다. feat 안에 버그 6개를, feat 전 커밋(diff 밖)에 대조군 버그 2개를 심고 같은 조건으로 리뷰를 세 번 돌렸다. 세 번 모두 버그 6개를 다 찾았고, 대조군과 그 밖의 지적은 하나도 없었다. 한 번에 에이전트 토큰은 8만 남짓이었다. 전체 리뷰(2026-11-15, 100만 가까이)와는 읽는 범위가 달라 배수로 비교할 값은 아니다. 다만 에이전트는 참조를 거의 따라가지 않았다. 그래서 grep 비용은 무시할 만큼 작았고, 대조군이 증명한 것도 "보고도 적지 않았다"가 아니라 "읽지 않았다"였다.

## Method

### 커밋 구성
측정용 로컬 브랜치 `benchmark/critical-hit`에 커밋 둘을 올렸다. 푸시하지 않았고, 측정 뒤 지웠다.

| 커밋 | 역할 | 내용 |
|---|---|---|
| `3b2ad38c` (A) | base | 대조군 버그 2개. 메시지는 눈에 띄지 않게 "refactor: 비교식 정리"로 했다 |
| `00ecdfed` (B) | commit | 가짜 feat와 그 안의 버그 6개. 9개 파일, 57줄 추가와 16줄 삭제 |

- 브랜치는 `feat/diff-review`(71ccbf2b) 위에서 땄다. 리뷰 도구가 아직 main에 없기 때문이다.
- 대조군을 feat 전 커밋에 넣은 것은 diff 밖에 두기 위해서다. 같은 커밋에 넣으면 diff에 들어가 대조군이 되지 못한다.

### 가짜 feat: 치명타
- 무기마다 치명타 확률(0~1)과 치명타 배율을 Definition(`WeaponComponent`)에 둔다. 처음에는 배율을 고정 상수로 하려 했으나, "수치는 Definition에 둔다"는 규칙과 부딪혀 Definition에 두었다.
- 공격 한 번마다 첫 발이 나갈 때 World의 시드 고정 난수로 치명타를 정한다(`PlayerActionStateComponent.isCriticalAttack`). 치명타면 그 공격의 모든 발의 피해(강화가 반영된 피해)에 배율을 곱한다.
- 근접, 직선 투사체, 포물선 투사체 공격 모두 해당한다. 적의 공격과 화면 표시는 바꾸지 않는다.
- 정상 동작하는 feat를 먼저 만들어 컴파일을 확인한 뒤, 그 위에 버그를 심었다.
- 심은 코드는 남기지 않았다. 버그마다 무엇을 어떻게 바꿨는지는 `answer-key.json`의 `change`에 있다.

에이전트는 세 번 모두 비슷하게 움직였다.
1. `git diff`로 바뀐 줄을 본다.
2. `cat -n`으로 바뀐 파일을 한꺼번에 읽는다.
3. 바뀐 심볼(`isCriticalAttack`, `criticalChance`, `_random`, `IsAttackingWith`)을 grep 한두 번으로 찾는다.

참조를 찾는 grep은 실행마다 0~2번이었다.

## Discussion

### 비용은 diff 크기를 따라간다
전체 리뷰보다 크게 줄었지만, 읽는 범위가 달라 배수로 비교할 값은 아니다. 이번 diff가 70줄 남짓으로 작았던 영향이 크다. diff가 커지면 늘겠지만, 폴더 전체를 읽던 때처럼 프로젝트 크기를 따라가지는 않는다.

### grep 비용은 무시할 만큼 작았다. 대신 참조를 거의 따라가지 않았다
참조를 찾는 grep은 실행마다 0~2번이었고, 비용의 대부분은 바뀐 파일을 읽는 데 들었다. 그래서 이번 결과로는 grep을 Roslyn 참조 도구로 바꿔도 아낄 비용이 거의 없다.

그런데 이것은 에이전트가 참조를 끝까지 따라가지 않았기 때문이기도 하다. 피해 요청을 받는 `DamageSystem`, 폭발을 판정하는 `ProjectileHitSystem`, 난수를 함께 쓰는 `EnemyBehaviorSystem`은 어느 실행도 읽지 않았다. 이번 버그는 모두 원인이 diff 안에 보였으므로 따라가지 않아도 찾을 수 있었다. 지침은 "World까지 계속 따라간다"이지만, 버그를 다 찾았다고 판단하면 거기서 멈추는 것으로 보인다.

### 대조군은 반만 증명했다
경로 밖 대조군(C2)은 읽지도 적지도 않았다. 범위를 벗어나 헤매지 않는다는 뜻이다. 하지만 경로 위 대조군(C1, `DamageSystem`)도 읽지 않았으므로, "diff 밖 버그를 보고도 적지 않는다"는 이번 측정으로 확인되지 않았다.

### 이번 재현율은 쉬운 조건의 값이다
버그 여섯 개가 모두 diff 안에 있었고, 원인이 바뀐 줄에 그대로 보였다. 전체 리뷰 측정(2026-11-15, 평균 86.7%)과 같은 잣대로 비교할 수 없다. 특히 놓치기 쉬운 경우를 시험하지 못했다. 원인이 바뀌지 않은 파일에 있어서, 참조를 따라가야만 보이는 버그다. 예를 들면 바뀐 필드의 뜻을 바뀌지 않은 System이 예전 뜻으로 읽는 경우다.

### `cat -n`으로 여러 파일을 이어 읽으면 줄 번호가 틀린다
run2는 파일 셋을 `cat -n` 한 번으로 읽어, 줄 번호가 파일을 건너 이어졌다. 그래서 두 지적의 줄 번호가 실제와 달랐다. 이슈 도구는 이 줄 번호로 코드에 링크하므로, 이대로 이슈를 만들면 링크가 엉뚱한 줄을 가리킨다. 리뷰 지침에 "파일은 하나씩 읽는다"를 더하면 막을 수 있다.

### 다음에 확인할 것
- 원인이 바뀌지 않은 파일에 있어서 참조를 따라가야만 찾는 버그. 이 경우의 재현율과, 그때의 참조 탐색 비용
- 경로 위 대조군을 에이전트가 반드시 읽게 되는 파일에 두는 방법. 예를 들어 바뀐 파일 안의 diff 밖 줄에 둔다
